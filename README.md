# Rabbit

面向独立授课者（语言老师、家教、乐器老师、私教、教练）的**预约与课时管理**工具。

> 让老师的排课和课时账，从微信聊天里搬出来。

可以理解为：**面向长期 1 对 1 服务关系的 Calendly + 轻量课时管理。**

---

## 产品形态

| | 形态 | 技术 |
|---|---|---|
| **老师端** | iOS App | SwiftUI（最低 iOS 17） |
| **学员端** | Web / H5 | 点老师分享的邀请链接即用，**不需要安装、不需要注册** |
| **后端** | 自有 REST API | Node.js + TypeScript |
| **数据库** | PostgreSQL 16 | 托管部署推荐 Supabase |

### 两个不能妥协的产品约束

1. **学员不能为了约一节课去装一个 App。** 学员发一条微信就能约到课，成本约等于零；多一次安装就会让他退回微信。这是本产品的头号风险（R1），学员端做 Web 就是为了对抗它。
2. **课时余额是钱，只能由服务端在事务里改。** 客户端的任何校验都只是体验优化。

## 三条最容易做错的地方

| # | 坑 | 为什么 |
|---|---|---|
| 1 | **时区** | 一律用服务端返回的展示串，客户端不做任何时区换算。学员把手机时区改成 UTC 就会看到错的课表，而这会变成一次"我明明约的是 3 点"的纠纷。禁止硬编码 `+8`。 |
| 2 | **展示与实际判定用同一个实现** | 「日历高亮」「时间列表」「确认预约」三处口径不一致，就会产出"列表里看着能约、点确认说冲突"的挫败感。这件事的落点是：**Slot 算法只在服务端有一份实现**。 |
| 3 | **课时账本** | 预约时**不扣课时**，只占用额度；真正扣减发生在课程完成或学员逾期取消。任何余额变动都必须经过唯一的 `applyPackageTransaction` 入口并留下流水，**不允许直接改数字**。最锋利的一条：**流水类型分成两簇，`purchased` 只由「购买量」簇（`PACKAGE_CREATED` / `MANUAL_ADD` / `PURCHASE_ADJUSTMENT`）改动**；「余额」簇（其余全部，含 `REVERSAL`）只动 `remaining`。**判断只看类型，永远不看金额正负** —— `REVERSAL` 是 `+1`，但它绝不能抬 `purchased`（用符号推断会让 `10/10` 撤销完成变成 `11/10`，而任何 CHECK 都不会报错）。 |
