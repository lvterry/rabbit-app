# 1. 项目概述

## 1.1 产品定位

一款面向独立授课者的**老师端 iOS App + 学员端 Web**，帮助老师、教练等个人服务提供者管理：可预约时间、学员、课程、课包与剩余课时、预约/改期/取消、上课记录。

老师端是原生 iOS App（SwiftUI，最低 iOS 17）；学员端是网页（H5），点老师分享的邀请链接即用。老师将自己的预约入口分享给授权学员，学员无需反复沟通时间，即可查看老师开放的时间并自主预约。

> **为什么学员端不做 App**：让学员为了约一节课去装一个 App，会直接加重 R1（§2.2）。学员的整个生命周期只有"看下一节 + 约一节"两件事，一个网页足够。多一次下载、多一次注册，都会把一部分学员推回微信。

> **面向长期 1 对 1 服务关系的 Calendly + 轻量课时管理。**

## 1.2 一句话价值

> 让老师的排课和课时账，从微信聊天里搬出来。

# 2. 目标与假设

## 2.1 用户问题

独立老师和教练目前依赖：

- 微信聊天确认时间
- 线下转账收费
- Excel / Notion / 备忘录记录课时
- 手机日历管理上课安排

学员数量上升后，重复沟通持续占用老师时间：

> "老师周六有时间吗？" / "下午三点可以吗？" / "我这周临时有事，能换到周日吗？" / "我现在还剩几节课？"

## 2.2 核心假设与风险排序

老师几乎一定愿意让学员自主预约——他是净收益方，省的就是他的时间。真正的阻力在学员侧：

> 学员发一条消息就能约到课，成本约等于零；而任何需要额外动作的入口——点开、授权、选日期、选时间、确认，还不一定约得上——都是在让他为一个"帮老师省事"的工具付出自己的操作成本。

**一条产品级硬约束：绝不能让学员为了约一节课去装一个 App。** 这条不只是"体验更好"——它是 R1 的直接推论：下载、安装、注册这一串动作的成本远高于"发条消息"，只要存在，一部分学员就会直接放弃，而老师看到的就是"学员不用"。

而且师生之间**已经存在一个免费、零学习成本的沟通渠道（微信）**。这是同类产品在"熟人长期关系"场景里最难的一关。因此：

### 风险排序

| 级别 | 风险 | 说明 |
|---|---|---|
| **R1（决定生死）** | 学员不愿意改变习惯，仍然回微信里约课 | 老师会因此放弃维护系统，产品退化成又一个 Excel |
| R2 | 老师嫌设置麻烦（课程 + 开放时间 + 学员 + 课包 4 步） | **正式待验证假设**：收益与成本谁大，必须由试点数据回答 —— 见下 |
| R3 | 课时账对不上，产生纠纷 | 影响留存与口碑，但可用流水与撤销兜底 |
| R4 | 时间冲突/重复预约 | 纯技术问题，可彻底解决 |

### R2 是一个待验证的假设，不是已知事实

老师得到的是**省沟通**的收益，同时要承担**维护 Availability / Student / Package / 例外时间**的成本。这两者谁大，不能靠"他是净收益方"来断言 —— 它是仅次于 R1 的风险，必须用试点数据回答。

两个要盯的数字：

1. **从注册到第一位真实学生收到邀请的耗时分布** —— 终点是"真实学生收到邀请"，不是"老师点完首次设置"。
2. **有多少老师在真正发出第一条邀请之前就停了** —— 这是激活漏斗上最直接的流失点。

> **推论**：Onboarding 坚持"**先加一个真实学生跑起来**"，不要诱导老师第一次就迁移几十位学生。一次性搬几十人，收益要等到第一位学生真的约上才出现，而设置成本先被放大几十倍。§10.1 的首次设置流程若与本条冲突，以本条为准调整措辞（流程本身不变）。

### 对 R1 的主动设计（不只是观察）

1. **让系统成为唯一权威账本。** 课时余额、已约课程只在系统里可查。老师不再口头报"你还剩 7 节"。
2. **让约课入口唯一。** 老师的对外话术变成"以后直接在这里约我的时间"，而不是"你微信跟我说"。
3. **降低学员单次操作成本到极低。** 学员端只有 2 个一级入口（§16.2）；从打开链接到预约成功不超过 3 次点击（日期 → 时间 → 确认），不引入登录引导页、不做课程介绍页。**零安装是这条的一部分。**
4. **学员端不做 App、不做注册墙 —— 邀请链接在浏览器里直接可用。** 这是一条产品级约束：任何"先装个 App 吧""先注册一下吧"的设计，都是把本该由老师承担的成本转嫁给学员，而这个成本高到足以让一部分人直接退回微信。
5. **设置反向护栏指标（§22.3）。** 如果"老师手动代约占比"长期高于 70%，那是一个**值得停下来复盘的信号** —— 它指向 R1 可能没有被解决，但结论要靠漏斗数据（§22.2）下，不能只凭这一条指标。

### MVP 要验证的核心假设

> **独立授课者是否愿意让已有学员自主预约开放时间，并通过一个统一工具管理预约和剩余课时。**

## 2.3 MVP 目标

1. 明显减少老师和学员之间的约课沟通。
2. 老师能清楚知道每天有哪些课程、每位学员还有多少课时。
3. **学员能在无需询问老师的情况下完成一次预约——且愿意做第二次。**

第 3 条的"第二次"是关键：一次性预约可能只是给老师面子；第二次才说明习惯真的改了。

## 2.4 MVP 暂不解决的问题

- 招生获客、CRM、在线营销
- 作业管理、教学内容管理、训练计划、疗愈记录
- 财务记账、发票、收入统计
- 员工管理、机构排课、多教练共管账户
- 支付、自动售卖课包

第一版只聚焦：**预约 + 学员 + 课时**。

> **关于 Recurring Booking 的假设（不是功能清单）**：MVP 明确不支持 Recurring Booking（§25），这隐含一个产品判断 —— **长期关系里仍有足够多的课需要学生反复主动选 slot**。
> Pilot 时只记录一个数字即可：**有多少预约其实是固定每周同一时间**（见 §22.2）。
> 如果这个比例很高，Recurring Booking 会很快升到 P1；如果多数人每周时间确实在变，当前方向会得到很强的验证。

# 3. 目标用户

## 3.1 Primary User — 老师

独立提供长期服务的个人授课者：语言老师、家教、钢琴/乐器老师、健身私教、瑜伽教练、舞蹈老师、艺术老师、其他一对一教练。

典型特征：

- 学员数量约 5–50 人（**注意：这意味着相当比例的用户就在 5 人附近，直接影响 §21 的商业化设计**）
- 大部分学员会长期重复上课
- 通过微信与学员保持联系
- 课程按次或课包收费
- 自己完成排课和学员管理
- 没有使用复杂机构 SaaS 的需求

老师群体的 iPhone 与 Apple ID 覆盖率很高——这是老师端选原生 iOS App、并用 Sign in with Apple 做登录的现实基础（§15.3）。

## 3.2 Secondary User — 学员

学员**不会主动寻找**一个排课工具。他进入产品的目的非常明确：

> 查看什么时候可以上课，然后完成预约。

因此学员端的每一个多余页面、每一次多余点击、每一次额外的安装或注册，都是在直接损耗 R1（§2.2）。

# 4. 核心产品原则

## 4.1 老师是付费用户

价值来自老师侧：减少沟通、减少冲突、管理课包、管理学生、记录课程。学生端免费。

## 4.2 学员关系优先于公开流量

这不是公开课程 marketplace。老师邀请已经认识的学员进入。核心关系是 `Teacher → Student`，而非 `Public → Search → Teacher`。

## 4.3 一个学员只看到与自己有关的信息

学员只能看到：自己可预约的课程、老师开放给自己的时间、自己的预约、自己的剩余课时。

学员无法看到：其他学员姓名、其他学员课程、老师完整私人日历。

**已被占用的时间只表现为"不可预约"，不显示占用原因。** 这条规则必须在 slot 返回结构里体现——不可用 slot 不返回、或返回时不含任何他人信息。

## 4.4 尽可能减少老师操作

可以自动完成的，就不要求老师手动维护：

| 行为 | 自动化 |
|---|---|
| 预约成功 | 自动进入日程，占用一个课时额度 |
| 课程完成 | 自动扣除 1 个课时 + 生成流水 |
| 取消预约 | 按规则自动判定是否扣课时 |
| 时间冲突 | 系统过滤，老师不需要记住谁什么时候有课 |
| **课程到期未处理** | **超过 N 小时自动按"已上课"结算（§10.8），老师可 7 天内撤销** |

最后一条直接来自本原则：让老师每天手动点"完成课程"是典型的可自动化操作。

## 4.5 数据只增不删

真实业务数据不物理删除，用状态表达（§20）。避免记录断裂。

# 5. 术语与数据模型

## 5.1 实体关系

```
User（账号，全局唯一）
  │
  ├─ AuthIdentity（1:N，登录方式：Apple / 邮箱）
  │
  ├─ TeacherProfile（1:1，老师资料 —— 有这一行才具备"老师能力"）
  │     ├─ Course（1:N）
  │     ├─ AvailabilityRule（1:N，每周重复）
  │     ├─ AvailabilityException（1:N，临时关闭）
  │     └─ Student（1:N，老师管理的学员）
  │           ├─ Package（1:N，课包批次）
  │           │     └─ PackageTransaction（1:N，课时流水）
  │           └─ StudentInvite（1:N，邀请）
  │
  └─（作为学员时）Student.user_id 指向本 User（**可空：学员默认没有账号**，见决定 5）

Booking（1 个时间段 = 1 条，属于 Teacher + Student + Course + Package）
  └─ Session（0 或 1 条，实际上课记录）
```

### 关键设计决定

> **本节只讲产品侧的数据模型决定。**「谁能做什么」—— Principal 的形态、每个接口的鉴权分类、幂等键挂在谁身上 ——
> 唯一权威定义见 `docs/auth-model.md`，本文不重复定义。
> 下面的决定 5 / 决定 6 是身份模型的产品侧取舍，`docs/auth-model.md` 直接引用它们。

**决定 1：`User` 是全局实体，`Student` 是关系实体。**

`Student = (User?, Teacher, 姓名, 状态)`。即：

- 学员在 A 老师处和 B 老师处是**两条 Student 记录**，但可以绑定**同一个 User**。
- 因此**有账号**的学员端首页需要支持"我绑定了多个老师"的结构（§16.2）。注意这条能力**依赖 `user_id`**：默认的免账号状态下，系统无法知道 A 老师的 Student 123 与 B 老师的 Student 456 是同一个人（见决定 5）。所以**多老师聚合是账号升级之后才成立的能力，不是匿名模式的默认能力**（见决定 6）。
- 老师也可能是别的老师的学员——不阻止，不做特殊处理。

> **不做机构/工作室账户、不做多教练共管同一个老师账号。** 学员绑定多个老师不在排除范围内。

**决定 2：`Package` 是批次，不是"余额容器"。** 见 §6。

**决定 3：`Booking` 同时绑定 `Course` 和 `Package`，但额度按 `(Student, Course)` 计算。** 见 §6.2。

**决定 4：身份与账号解耦。**

`User` 不再等于某个平台的登录凭证。`AuthIdentity(provider, subject)` 承载"这个账号是用 Apple 登录的，还是用邮箱登录的"，同一个 `User` 可以挂多种身份。

- `User` = 业务主体：老师资料、学员关系、课时账都挂在他身上。
- `AuthIdentity` = 登录方式：换设备、换 Apple ID、先用邮箱登录后来再绑 Apple，都只是**给同一个 User 增加或替换一条身份**，不会新建 User，也不会把课时和预约拆成两份。
- **这条决定在学员端 Web 上尤其重要**：学员可能先用邀请链接进入、看到"X 老师邀请你加入"、之后再补一个登录方式（邮箱魔法链接或 Apple 登录）。如果 `User` 就等于登录凭证，"先看后登"这个流程根本没有位置可以落——而学员端的每一步额外动作都在损耗 R1（§2.2）。

**决定 5：学员默认没有账号 —— 邀请 token 就是身份。**

> `Student.user_id` **允许长期为空，这是默认状态，不是异常状态。**

账号登录在这个场景里摩擦很高：邮箱魔法链接要求一次上下文切换（去邮箱、再切回来），网页版 Apple 登录要若干次点击甚至 2FA 与密码。而学员的替代方案始终是"给老师发一条消息"，成本约等于零。

因此本方案的选择是：**消费邀请 token 直接换取该学员的会话，绑定不需要任何账号。**

| 路径 | 行为 |
|---|---|
| **默认（免账号）** | 打开链接 → 看到"X 老师邀请你加入" → 点「接受邀请」→ 服务端消费 token、签发该 Student 的会话 → 直接进入「我的课」。**全程不出现登录页。** `user_id` 保持为空 |
| **升级（可选）** | 学员想换设备或找回访问时，用 Sign in with Apple 或邮箱魔法链接把会话升级为账号，此时才回填 `user_id`。教师端也会因此看到"已绑定 · 账号邮箱 XXX"，便于人工核对 |

- **不变式 I6 的范围是有账号的学员**：索引写成部分唯一索引 `UNIQUE (teacher_id, user_id) WHERE user_id IS NOT NULL`（见 `docs/data-model.md`）。
- **代价（必须知道）**：清空浏览器数据或换设备后，学员会失去访问权，需要老师**重新发送邀请**。这是**有意把摩擦从"每个学员、每一次进入"降级为"极少数情况下的一次找回"** —— 老师的 Student Detail 里已经有这个入口（§10.2）。
- 老师可以在学员完全没有账号的情况下给他建课包、手动创建预约。

**决定 6：匿名会话一次只服务一个老师关系。**

免账号的代价不止"换设备要重发邀请"这一条，还有一条必须在产品上认下来：

> **在默认的匿名状态下，系统不知道 A 老师名下的 Student 123 与 B 老师名下的 Student 456 是同一个人。**

会话的身份是 `(student_id, teacher_id)` 作用域（见 `docs/data-model.md` §2.2c），浏览器里也只持有一个学员会话。因此：

| 情形 | MVP 行为 |
|---|---|
| 学员只有一位老师（**绝大多数**） | 首页就是一位老师、几门课。这是默认路径，也是全部优化对象 |
| 学员在同一位老师处有多门课 | 首页按课程卡片展示，不受影响 |
| 学员收到**第二位老师**的邀请 | 页面明确说明会发生什么，让学员自己选：「升级为账号」（推荐，之后两位老师都能看到）或「只使用这位老师」（替换当前匿名会话） |
| 已升级为账号 | `student-home` 自然返回多张卡片，首页显示老师列表 |

**明确不做：不设计"本地身份钱包"**（把多条匿名会话存在浏览器里再聚合展示）。那会让"免账号"这个本来很干净的设计长出一套客户端身份管理，而它一旦要处理会话失效、跨设备与冲突合并，成本会超过它解决的问题。

**被替换掉的那个关系不会丢数据**：A 老师的 Student 记录、课时、预约、流水全部在服务端保留，只是当前浏览器不再持有它的会话。学员想回去，路径是老师重发邀请，或自己升级账号。

> 代价是诚实的：**一个匿名学员无法在同一个浏览器里同时使用两位老师。**
> 这个取舍基于一个判断 —— MVP 阶段"一个学员同时被两位都在用本产品的老师服务"是罕见情形，为它增加复杂度不划算。
> 如果数据表明这个比例可观，正确的解法是**把账号升级做得更顺**，而不是给匿名模式加身份管理。

## 5.2 术语表

| 术语 | 含义 |
|---|---|
| **Availability** | 老师每周重复的开放时间规则（如"周二 14:00–18:00"） |
| **Exception** | 对 Availability 的临时覆盖（整天关闭 / 区间关闭） |
| **Slot** | 一个可被预约的具体起止时间，由 Availability + Course 时长 + 占用情况推导，**不落库** |
| **Booking** | 一条预约记录（一个被占用的时间段） |
| **Session** | 一次"实际上过"的课，由 Booking 完成时生成，**迟到取消不生成 Session** |
| **Package** | 一个课包批次：一批课时，有累计购买量和当前余额 |

# 6. 课时模型

## 6.1 批次模型

**一个 `Package` 代表一批购买的课时，不再代表"某学员某课程的余额"。**

- `purchased_sessions`：这一批一共买过多少节。**只增不减**（除撤销）。
- `remaining_sessions`：这一批还剩多少节。
- 不变式：`0 ≤ remaining ≤ purchased`。

### 为什么用批次模型

若把"某学员某课程的余额"当成一个容器、续课时直接给当前 Package 增加课时，只有两种做法，且都不可接受：

- 若累计购买量不改 → 余额涨到 17，UI 显示「剩余 17 / 10」；
- 若累计购买量改成 20 → 既有记录里"上完 3/10 节"的语义作废。

批次模型下 `purchased` 与 `remaining` 同向上涨，**`remaining > purchased` 在结构上不可能发生**，`remaining / purchased` 永远是一个有意义的展示。

## 6.2 余额、占用与可用额度

额度按 `(Student, Course)` 聚合，跨该学员该课程下的所有**未归档批次**：

```
remaining_sessions  = Σ(未归档 Package 的 remaining_sessions)
reserved_sessions   = count(status = Upcoming 的 Booking)
                      where student = S and course = C
available_sessions  = remaining_sessions − reserved_sessions
```

- `reserved` 与 `available` 都是**派生值，不落库**，避免两处状态不一致。
- **已过期但尚未结算**的 Upcoming Booking **仍计入 reserved**，直到被结算（完成 / 自动结算 / 取消 / 迟到取消）。这防止同一节课被重复占用。
- 时间冲突是**老师级**的（一个老师同一时刻只能上一节课）；额度是 **(学员, 课程) 级**的。两者独立。

例：学员在西语课包剩 3 节，已约 2 节未来的课 → `reserved = 2`，`available = 1`，最多还能再约 1 节。

## 6.3 消耗顺序

一个学员同一课程下可能有多个未归档批次（续课后常见）。**消耗顺序 = 最早创建且 `remaining > 0` 的批次优先（FIFO）。**

- `Booking.package_id` 在**创建预约时**按此规则写入，但**不在创建时扣减**（§6.4）。
- 老师在创建预约时可以手动指定批次（可选，UI 默认隐藏，用于纠错场景）。
- 若 FIFO 选中的批次在结算前被归档，结算时按当时的 FIFO 重新选择。

## 6.4 预约时不扣课时，只占用额度

创建 Booking **不修改** `remaining_sessions`，只让 `reserved` +1。

真正扣减发生在两个时刻：

| 时刻 | 流水类型 |
|---|---|
| 课程完成 / 自动结算 | `SESSION_COMPLETED` |
| 学员逾期取消 | `LATE_CANCEL` |

## 6.5 续课

**默认方式：新建一个批次。** 老师点"续课 +10 节" → 创建新的 `Package`（同 Student、同 Course，`purchased = remaining = 10`），同时写一条 `PACKAGE_CREATED`。

- 旧批次余额用完自动转 `Used Up`，记录保留。
- 新批次 `created_at` 更晚，因此排在 FIFO 后面 —— 旧课时先消耗，符合直觉，也不浪费。

**例外方式：`MANUAL_ADD` 给现有批次加课时。** 用于"上次记错了""这一批补送 2 节"。此时 `purchased` 与 `remaining` 同步上涨，不变式保持。

> MVP 的 UI 只需要暴露"续课"（新批次）一个入口。`MANUAL_ADD` 放在"调整课时"里（§12）。

## 6.6 展示口径

| 位置 | 显示 | 规则 |
|---|---|---|
| 学员端首页（每个课程） | **剩余 N 节** | 只显示聚合余额，不显示分母 |
| 学员端（该课程只有 1 个未归档批次时） | 剩余 N / M 节 | 分母 = 该批 `purchased`，此时它有意义 |
| 老师端 Student Detail → 课包 | 批次列表，每批 `remaining / purchased` + 状态 + 创建时间 | 多批次一目了然 |
| 老师端 Student Detail → 顶部摘要 | 剩余 N 节 · 已约 M 节 | `M = reserved`，帮助老师理解"为什么学员约不了" |
| 任何位置 | **不显示 `reserved` 给学员** | §4.3 |

## 6.7 批次状态

| 状态 | 条件 | 行为 |
|---|---|---|
| `Active` | `remaining > 0` 且未被归档 | 参与余额聚合与 FIFO |
| `Used Up` | `remaining = 0` | 不参与余额聚合；记录保留；老师可 `MANUAL_ADD` 使其回到 Active |
| `Archived` | 老师主动归档 | 不参与余额聚合与 FIFO；记录保留；可恢复为 Active |

**边界：允许归档一个 `remaining > 0` 的批次**（老师停止授课时必然如此）。此时 UI 必须明确提示：

> 归档后剩余 N 节将不可用于预约，记录仍会保留。

不提供"作废课时"操作——余额原样留着，作为既有事实。

# 7. Availability 与 Slot 生成

本节把 slot 的生成规则定死。

## 7.1 开放时间

老师在「开放时间」里配置**每周重复**的区间：

```
周二  14:00–18:00
周四  14:00–18:00
周六  09:00–17:00
```

- 同一个 weekday 允许多个区间。
- 区间不支持跨天（`start < end`，同一天内）。
- 时区固定 `Asia/Shanghai`，展开时按老师本地时间计算。

## 7.2 临时关闭

老师可以对某个日期设置 Exception：

- 整天关闭（vacation / personal day）
- 关闭某个区间（如"周六 12:00–14:00 有事"）

**已存在的 Booking 不会被自动取消。** Exception 只影响之后生成的 slot。如果老师想取消已约的课，必须显式取消相应 Booking（这样学员才会收到通知，课时规则才会生效）。

## 7.3 Slot 生成算法

给定 `teacher_id`、`course_id`、本地日期 `D`：

```
1. 取该 D 对应的 AvailabilityRule 区间集合 A
   若 D 命中整天 Exception → A = ∅
2. 构造占用集合 B：
     B = { [b.start_at, b.end_at) | b.teacher_id = teacher, b.status = Upcoming }
       ∪ { 该日 Exception 的区间（若有） }
3. duration = Course.duration_minutes
   step     = Teacher.slot_step_minutes   （默认 30）
4. 对每个 a ∈ A：
     从 t = a.start 开始，按 step 步进：
       若 t + duration > a.end  → 该区间结束
       若 [t, t + duration) ∩ B = ∅ → 产出 slot t
       t += step
5. 按时间升序返回
```

### 规则要点

- **对齐**：slot 从 Availability 区间的起点对齐（不是从整点对齐）。若开放时间是 14:00–18:00、step 30，则 slot 为 14:00 / 14:30 / 15:00 / …。若开放时间是 14:10 起，则从 14:10 起。可预测比"看起来整齐"重要。
- **不跨出开放区间**：必须满足 `t + duration ≤ a.end`。
- **step 与 duration 解耦**。若隐含 `step = duration = 60`，14:00–18:00 开放、15:00 被占时只能约 14:00 / 16:00 / 17:00。默认 `step = 30` 时同场景产出 **14:00 / 16:00 / 16:30 / 17:00**，可约集合是前者的超集，对老师和学员都更灵活。
- **不同时长的课程互不干扰**：学员先选课程，再看该课程的 slot。**不把多个课程的可约时间混在一个列表里**——这直接消除了"60min 和 90min 课程共享一段开放时间时怎么切"的歧义。
- **不设缓冲时间**：两节课可以背靠背（14:00–15:00 与 15:00–16:00）。MVP 不做；若老师需要，后续加 `buffer_minutes`。
- **不支持跨天**：`Course.duration_minutes ≤ 240`，且必须完整落在区间内。
- **不存在"取消即恢复"的额外逻辑**：Booking 转 Cancelled 后自动从 B 中消失，slot 立即重新出现。

## 7.4 可用性判定的四层检查

| 层 | 时机 | 目的 |
|---|---|---|
| L1 | 查询 slot 列表 | 过滤冲突与规则不符，给学员看到干净的可选集合 |
| L2 | 学员点"确认预约"前 | 重新拉一次该 slot 状态（防 stale UI） |
| L3 | 服务端创建事务内 | 原子冲突检查 + 额度检查，失败则整体回滚 |
| L4 | 数据库排他约束（`EXCLUDE`） | 兜底，防止极端并发下的漏网（§13） |

创建 Booking 必须同时满足：

- Student 存在且 `status = Active`
- 请求者对该 Student 有权（判权一律走 Principal，规则见 `docs/auth-model.md` §3.2 / §3.3，**不看 `student.user_id`**）
- Course 存在且 `status = Active`、`allow_self_booking = true`（学员自主预约时）
- 该 `(Student, Course)` 下 `available_sessions ≥ 1`
- `start_at` 落在某条 AvailabilityRule 区间内且不跨区间
- `start_at ≥ now + min_lead_hours`
- `start_at ≤ now + max_advance_days`
- 不命中 Exception
- 与老师所有 Upcoming Booking 无重叠

### 老师手动创建预约的越权

老师创建预约时（T04），**跳过 Availability 与提前/最远时间检查**（老师有权给自己加课），但**仍然强制检查时间冲突**。

若该时间段不在开放时间内，UI 提示：

> 该时间不在你的开放时间内，学员将无法自主预约此时间。仍要创建吗？

# 8. 预约规则

MVP 支持三组规则，在「我的 → 预约规则」配置：

| 规则 | 默认 | 可选 |
|---|---|---|
| 最少提前预约 `min_lead_hours` | 2 小时 | 0 / 1 / 2 / 6 / 12 / 24 |
| 最远可预约 `max_advance_days` | 30 天 | 7 / 14 / 30 / 60 |
| 免费取消期限 `free_cancel_hours` | 24 小时 | 6 / 12 / 24 / 48 |

规则变更**对已存在的 Booking 不生效**——每条 Booking 在创建时把当时生效的 `free_cancel_hours` 快照到自身（`policy_snapshot` 字段），避免老师改规则后学员突然被扣课时引发争议。

> 之所以要快照：老师改了取消期限后，"已有的课按哪个期限算"必须有确定答案，否则最容易吵架。

# 9. 状态模型与迁移

## 9.1 Booking 状态

```
Upcoming ──→ Completed   （完成 / 自动结算）
    │
    └──────→ Cancelled   （老师取消 / 学员取消 / 改期）
```

只有三个状态。**不增加 Pending / Confirmed / Rescheduled / No-show / Refunded。**

## 9.2 迁移表

| 起始 | 事件 | 结束 | 条件 | 副作用 |
|---|---|---|---|---|
| — | 创建预约 | `Upcoming` | §7.4 全部通过 | `reserved +1`；通知老师 |
| `Upcoming` | 老师点"完成课程" | `Completed` | 幂等（§13） | 建 `Session`；`SESSION_COMPLETED −1`；`reserved −1`；通知学员 |
| `Upcoming` | 自动结算 | `Completed` | `now > end_at + auto_settle_hours` | 同上，`Session.source = AutoSettled` |
| `Upcoming` | 学员取消 | `Cancelled` | `now ≤ start_at − free_cancel_hours` | `reserved −1`；`policy = FREE_CANCEL` |
| `Upcoming` | 学员逾期取消 | `Cancelled` | `start_at − free_cancel_hours < now < start_at` | `reserved −1`；`LATE_CANCEL −1`；`policy = LATE_CANCEL` |
| `Upcoming` | 老师取消 | `Cancelled` | 任意时刻 | `reserved −1`；**不扣课时**；`policy = TEACHER_CANCEL` |
| `Upcoming` | 改期 | → 新 `Upcoming` + 旧 `Cancelled` | 见 §10.7 | 见 §10.7 |
| `Upcoming` | （已开始未结算） | 仍 `Upcoming` | — | 进入老师端"待处理"分组；学员无法取消 |
| `Completed` | 撤销完成 | `Upcoming` | 7 天内 | `Session → Voided`；`REVERSAL +1`；`reserved +1` |
| `Completed` | — | 终态 | | 除撤销外无迁移 |
| `Cancelled` | 再次完成 / 改期 | — | | **禁止**（改期需新建） |

### 非法迁移（必须报错，不能静默）

- `Completed → Cancelled`
- `Cancelled → Completed`
- `Cancelled → Upcoming`（除撤销完成这条路径外不存在）
- `Completed → Completed`（重复完成）
- `Cancelled → Cancelled`（重复取消）
- 学员对已开始的 Booking 执行取消（应引导至 §10.8）

## 9.3 Session 状态

| 状态 | 说明 |
|---|---|
| `Active` | 正常上课记录 |
| `Voided` | 被撤销完成而作废，**不删除**（§4.5） |

## 9.4 Package 状态迁移

| 起始 | 事件 | 结束 |
|---|---|---|
| — | 创建 | `Active` |
| `Active` | `remaining` 归零 | `Used Up` |
| `Used Up` | `MANUAL_ADD` | `Active` |
| `Active` / `Used Up` | 老师归档 | `Archived` |
| `Archived` | 老师恢复 | `Active` 或 `Used Up`（按 `remaining` 判定） |

## 9.5 StudentInvite 状态

`Pending → Consumed`（绑定成功）/ `Expired`（过 `expires_at`）/ `Revoked`（老师主动作废）。`Consumed` 与 `Revoked` 为终态。

# 10. 核心流程

## 10.1 老师首次设置

```
Sign in with Apple → 创建老师资料（姓名 + 头像）
        → 创建第一门课程（名称 + 时长，默认 60min）
        → 设置每周开放时间
        → 确认预约规则（用默认值即可，允许跳过）
        → 进入「今天」
```

**允许跳过预约规则配置，直接使用默认值。** 把"设置预约规则"设为必经步骤，是激活漏斗里最没必要的一关（R2）。

> **首次设置的终点不是"配置齐全"，而是"第一位真实学生收到邀请"。** 这是 §2.2 的 R2 假设的直接推论：流程本身不变（上一步仍是「进入今天」），但引导话术要去掉"批量导入/一次迁移几十位学生"的暗示 —— 先加**一个真实学生**把闭环跑起来，其余的人等他看到第一节课真的约上之后再补。

## 10.2 添加学员与邀请

```
老师 → 学员 → + 添加学员
     → 输入姓名
     → 选择 Course
     → 输入初始课时（新批次）
     → 创建 → 生成邀请（一次性 token）
     → 通过 iOS 系统分享面板把普通 https 链接发给学员
       https://<domain>/i/<token>
       （也可以展示二维码让学员当面扫）
     → 学员在浏览器里打开 Web 版（不需要装 App、不需要注册、不需要登录）
     → 看到"X 老师邀请你加入"
     → 点「接受邀请」
     → 直接进入「我的课」（token 即身份，见 §5.1 决定 5）
```

每一跳的设计意图：

- **普通 https 链接，永远在浏览器里打开**：老师 App 不 claim `/i/*`，也不 claim 任何 https 路径（`docs/impl-guide.md` §8.4）。学员不需要先知道"要装什么"，也不需要在"App 还是网页"之间做选择 —— 那里根本没有选择。**老师自己收到另一位老师的学员邀请时也走 Web**：他和学员用的是同一个学员端，而老师端 App 里根本没有学员端页面可落（§5.1 决定 1 明确支持"老师同时是别人的学生"）。
- **不强制注册，也不强制登录**：打开链接先看到"X 老师邀请你加入"这个具体的事，点一下就进去了。消费 token 即建立该学员的会话（§5.1 决定 5），**默认路径上不存在登录页**。身份与账号解耦（§5.1 决定 4）是这件事的前提：登录方式是可选的升级项，不是进入的门票。
- **不要在这一步加任何"顺便完善资料"**：学员此刻的意图非常窄——看看还剩几节课、约下一节。任何额外表单都在直接损耗 R1（§2.2）。
- **系统分享面板**：老师从 App 内直接调起系统分享（微信、短信、邮件、AirDrop、复制链接都行），产品不必自己实现一套社交分发。
- **二维码**是分享面板的补充，用于当面场景（老师在场时最快）。

### 邀请机制

| 项 | 规则 |
|---|---|
| token | 一次性、不可猜测（≥128 bit 随机） |
| 有效期 | 默认 7 天 |
| 消费 | 学员点「接受邀请」后立即置 `Consumed`，不可重复使用（**不要求他先有账号**） |
| 重发 | 老师可"重新发送邀请"，旧的置 `Revoked`，签发新 token |
| **被转发给第三人** | 无会话（或会话属于别的学员）时打开已消费的邀请 → 提示"该邀请已被使用，请联系老师重新发送"，**不泄露任何身份信息**；**不做"谁先点谁绑定"** |
| **原学员再次打开已消费的邀请** | **不是错误**：识别出会话属于该邀请的 Student 后直接进入「我的课」，见下节《回到入口》 |
| 学员侧已绑定其他老师 | 允许；但匿名会话同一时间只服务一个老师关系（§5.1 决定 6） |
| 账号邮箱 / 昵称与老师录入的姓名不一致 | **静默绑定**，不要求二次确认。老师端展示"已绑定 · 账号邮箱 / 昵称 XXX"供人工核对；学员未升级账号时显示"已绑定 · 未设置账号" |
| 学员尚未升级为账号 | **这是默认状态**：`user_id` 为空，但预约、课时、既有记录一切正常。老师可正常为其手动创建预约 |
| 学员清了浏览器数据 / 换了设备 | 访问权丢失 → 老师「重新发送邀请」签发新 token（这是免账号方案的已知代价，见 §5.1 决定 5） |

> **邀请链接是学员端的唯一入口。** 学员端没有"搜索老师""浏览课程"这类入口，一切的起点都是这条链接。因此：链接必须是**一个普通的 https 地址、永远在浏览器里打开**（§16.2 S05 是它唯一的落地页），token 必须不可猜测、可撤销。这条链路上任何一环坏掉（域名证书、Web 部署、邮件进垃圾箱），学员侧就直接归零。

**一个 Student 最多绑定一个 User；一个 User 在同一 Teacher 下只能绑定一个 Student**（不变式 I6，部分唯一索引 `WHERE user_id IS NOT NULL`）。没有账号的学员不参与这条约束。若学员误绑到错误的 Student 记录，MVP 由老师修改学生姓名对齐——不做解绑流程（P1）。

### 回到入口：第二次怎么走（**核心功能，不是兜底**）

North Star 是"每位活跃老师每周由学员自主完成的预约数量"（§22.4），核心漏斗是**首次自主预约 → 第二次自主预约**（§22.2）。所以"学员第二次怎么回来"和"第一次怎么进来"是同等重要的设计对象。

第一次进入的路径之所以顺畅，是因为**他刚在微信里收到那条链接**。但两周以后，他很可能仍然回到微信里翻那条消息、点同一个 `/i/<token>` —— 而此时 token 已经被消费。如果这时只回一句"该邀请已被使用"，我们就把一个本来打算回来的学员挡在了门外。

**规则：`/i/<token>` 在任何情况下都先解析当前会话，再决定展示什么。**（判权与身份解析的权威定义见 `docs/auth-model.md` §3.1；这里只讲产品行为。）

| token 状态 | 当前会话 | 行为 |
|---|---|---|
| `Pending` | 任意 | 正常预览页（"X 老师邀请你加入" + 「接受邀请」） |
| `Consumed` | **会话的 `student_id` 正是这个邀请的 Student** | **不算错误**：直接进入「我的课」，同时把 URL replace 成 `/`，并滑动续期该会话 |
| `Consumed` | 无会话，或是**另一位**学员的会话 | 显示"该邀请已被使用，请联系老师重新发送"。**不泄露老师姓名、学员姓名或课程信息** |
| `Expired` / `Revoked` | 任意 | 显示"该邀请已失效，请联系老师重新发送"，同样不泄露任何身份信息 |

五条关键点：

- **"已被使用"只对无法证明身份的人显示。** 对原学员来说，那条链接就是他的入口，不是一次错误。
- **安全边界没有被放松**：换一个浏览器、没有会话的第三人打开同一条已消费链接，仍然被拒绝（同 §10.2 邀请机制的"不做谁先点谁绑定"）。
- **接受邀请后立刻 `history.replaceState('/')`。** 不要让浏览器长期停在一次性 token 的 URL 上 —— 它会被加书签、被加入主屏幕、被浏览器同步、被截图转发，而那个 URL 只会失效。
- **`/` 是正式入口，必须能独立工作**：

  | 会话状态 | `/` 的行为 |
  |---|---|
  | 无会话 | 中性提示"请从老师分享的邀请链接进入"，**不展示任何数据** |
  | 学员会话 | 直接渲染「我的课」（§16.2 S01） |
  | 老师账号 | 提示老师请用 iOS App，并给出 App 入口 |

- **接受邀请成功后给一次可关闭的提示**："把这一页加入书签或添加到主屏幕，下次直接从里进。" 这是把"第二次回来"从"依赖微信聊天记录"变成"依赖浏览器入口"的最低成本手段 —— 只出现一次，不阻塞任何操作。

> **已知且接受的缺口**：学员清空浏览器数据后，会话与 token 一起失效，只能请老师重发邀请。这与 §5.1 决定 5 的代价是同一件事，没有额外变差。
> P1 可考虑把已消费的 token 与首次消费的设备做一次性绑定，让 cookie 丢失后仍能恢复；**MVP 不做** —— 它本质上是一个受限的本地身份凭证，会重新引入我们刻意避开的复杂度与攻击面。

## 10.3 学员自主预约

```
打开邀请链接 / 网页（我的课）
  → 看到：老师 / 课程 / 剩余 N 节 / 下一节
  → 点「预约课程」
  → 选日期（只高亮存在可用 slot 的日期）
  → 选时间（按 §7.3 生成）
  → 确认页：课程 / 日期 / 起止时间 / 老师
  → 点「确认预约」
  → L2 重新校验 → L3 事务内创建 → L4 约束兜底
  → 成功 → 通知老师
```

**学员端 Web 的硬约束：从打开链接到预约成功不超过 3 次点击**（日期 → 时间 → 确认），**不含安装、不含注册**。这是 §2.2 对抗 R1 的关键设计约束——Web 端多了一跳（浏览器），所以每一步的容错余地比 App 内更小，不能靠"再引导一下"来补。

接受邀请后 URL 立即被 replace 成 `/`（§10.2《回到入口》），此后**学员的正式入口是 `/`**，不再是那条 token 链接。

## 10.4 课程完成

老师端 → 某个 Booking → 「完成课程」

```
Booking → Completed
Session 创建（status = Active, consumed = 1）
PackageTransaction: SESSION_COMPLETED, −1
reserved −1
学员看到新余额
```

**幂等要求**：连续点击、网络重试都只能产生一次 Session 与一条流水（§13）。

## 10.5 撤销完成

老师端 Booking Detail → 「撤销完成」，**7 天内可用**（可配置）。

```
Session → Voided（不删除）
PackageTransaction: REVERSAL, +1
Booking → Upcoming
reserved +1
```

用途：老师点错了、临时把课挪到别的时间、记错了学员。

**这是老师端必须有的功能**——独立老师产品没有后台；若只留"开发阶段先人工修正"这条口子，每次都要直接改数据库，等于把操作成本转嫁给自己。

## 10.6 学员取消

```
学员 → Booking Detail → 取消
  → 服务端用服务器时间判定（§11）
  → 若 FREE_CANCEL：直接取消
  → 若 LATE_CANCEL：提示"此次取消将计为一次课程"
  → 学员确认
  → Booking → Cancelled
  → 时段立即释放
  → 扣 1 课时（LATE_CANCEL 流水，不创建 Session）
  → 通知老师
```

**判定时机是同步的**：在取消请求的同一个事务里用服务器时间判定，记录 `cancellation_policy_result`。**不依赖定时任务**——定时任务会引入"提交时算免费、处理时已超期"的争议。

**已开始的 Booking，学员不能取消**（§9.2 非法迁移），UI 显示：

> 这节课已经开始，请联系老师确认。

## 10.7 改期

### 核心矛盾与解法

Upcoming Booking 占用一个课时额度，因此"先创建新的、再取消旧的"会撞上额度检查：

> 学员余额 3 节、已约 3 节，想改其中一节 → 建新 Booking 时 `available = 3 − 3 = 0` → **创建失败**。
> 他明明有课，却改不了期，而且看不出原因。

**解法：改期收敛为单个数据库事务，在一个事务内完成"取消旧的 + 创建新的"两个动作。**

### 顺序：先取消、后创建

"先创建新的，再取消旧的"只在两个操作分属两个事务时才成立；在单个事务内，正确顺序是**先取消、后创建**：

- 若新 Booking 创建失败（时段被抢 / 额度不足），**整个事务回滚，旧 Booking 自动恢复为 Upcoming**，不存在"旧时段丢了"的问题。
- 先取消才能覆盖一个真实场景：**改期到与原时段重叠的时间**。例如 15:00–16:00 想挪到 15:30–16:30，若先创建，新 Booking 会与尚未取消的旧 Booking 撞上时间排他约束而失败。
- 先取消让额度检查变得平凡：旧 Booking 已是 Cancelled，`reserved` 的聚合自然把它排除，**不需要 `+1` 补丁**。

### 事务步骤

```
1. 读旧 Booking，取得 student / course / package / reschedule_count
2. 复核 status = 'Upcoming'、改期次数上限
3. 判定 policy（与 §11 取消规则完全同一套）
4. 取消旧 Booking（条件更新），写入 rescheduledTo = 新 id
5. 若 policy = LATE_CANCEL，**先结算旧 Booking 的 1 个课时（penalty）**
6. 走创建预约路径 —— 事务内做冲突检查与额度检查（§13.1）
   此时旧 Booking 已是 Cancelled，额度与冲突检查天然把它排除；且 penalty 已经扣掉
7. 创建成功 → 回填新 Booking 的 rescheduledFrom / rescheduleCount
```

> ★ **penalty 必须在创建之前结算**（第 5 步不能挪到第 7 步）。顺序反过来，额度检查看到的恰好是
> "旧单刚取消、额度短暂释放"的那个瞬间，会造出一节 `remaining = 0 / reserved = 1 / available = −1`
> 的未来预约 —— 一节**永远无法结算**的课。原因是 `available` 是派生值不落库，`I1` 只管 `remaining`，
> 所以数据库不会拦。完整推演与执行顺序见 `docs/data-model.md` §5.5。

**取消与创建之间不需要额外的锁**：取消只会释放，不会新增占用（§13.2）。

净效果：`reserved` 不变（旧的 −1、新的 +1），时段原子切换。

> **PostgreSQL 提供真正的多行事务**，所以上面写的"任一步失败整体回滚"可以按字面实现：
> 新建失败 → 整个事务回滚 → 旧 Booking 自动恢复为 Upcoming，不存在"改期失败却白扣一节课"。
> 两个回填 `rescheduledTo` / `rescheduledFrom` 也在同一事务内完成，因此 I8 不需要事后修复（§5.4）。
> 实现细节见 `docs/data-model.md` §5.5。

### 学员改期的课时规则

| 情形 | 规则 |
|---|---|
| `now ≤ start_at − free_cancel_hours`（免费期限内） | 免费改期，不扣课时，旧 Booking 记 `FREE_CANCEL` |
| 已逾期 | **按 `LATE_CANCEL` 结算旧 Booking（扣 1 课时）**，然后创建新 Booking |

> ★ **逾期改期需要额外的 1 节可用课时。** 它的产品语义是：**损失旧课时 + 新预约还需要另一节可用课时** ——
> 也就是一次要花掉两节，一节赔给已经浪费掉的时段，一节用于新的预约。
> 因此**最后一节课逾期改期会失败，且整体回滚**：旧 Booking 完好保留为 `Upcoming`，**不扣任何课时**。
> 客户端据此返回专门的错误码 `409 LATE_RESCHEDULE_INSUFFICIENT`，文案：
>
> > 本次改期已超过免费期限，需要额外消耗 1 节课。当前剩余课时不足，请先联系老师。
>
> 执行顺序（penalty 结算必须在新 Booking 创建**之前**）与逐步推演见 `docs/data-model.md` §5.5，
> 错误码全项目清单见 `docs/slot-algorithm.md` §6.5。

**为什么逾期改期和逾期取消扣一样多**：从老师角度，"课开始前 2 小时通知我换时间"和"直接取消"占用的成本完全相同（时间已经空出来了）。**规则不一致才是争议的源头**，所以 MVP 用一条规则覆盖两种操作。学员端在确认前必须明确提示：

> 此次改期将计为一次课程。

> P1 可放宽为"每自然月首次逾期改期免扣"，但**不进 MVP**。

### 改期次数上限

`reschedule_count` 默认上限 **3 次**。超过后学员端不再显示"改期"，提示：

> 该课程已改期 3 次，请联系老师。

理由：防止用改期反复占位、挤占其他学员的可约时间。老师改期不受此限制。

### 老师改期

不受免费期限约束、不扣课时、不计入 `reschedule_count` 上限。旧 Booking 记 `TEACHER_CANCEL`。

## 10.8 逾期未处理

**"学员不取消也不来"是这个品类最高频的真实情形，必须有明确的处理路径。**

规则：**不新增 No-show 状态**，只是在老师端增加一个"待处理"分组和一套结算动作。

```
课程结束时间已过，Booking 仍是 Upcoming
  → 出现在老师端「今天」的「待处理」分组
  → 学员端只读，不显示取消按钮
```

老师可执行三个动作：

| 动作 | 结果 | 流水 |
|---|---|---|
| 完成课程 | `Completed` + Session | `SESSION_COMPLETED −1` |
| **标记未上课并扣课时** | `Cancelled`，无 Session | `LATE_CANCEL −1`（`policy = LATE_CANCEL`） |
| 免扣取消 | `Cancelled`，无 Session | 无（`policy = TEACHER_CANCEL`） |

### 自动结算

默认 `auto_settle_hours = 24`：课程**结束**后 24 小时内老师未处理，系统自动按"完成课程"结算（`Session.source = AutoSettled`）。

> **锚点是 `end_at`，不是 `start_at`。** 用户心智里的规则是"课程**结束** N 小时后仍未处理 → 自动完成"；
> 用 `start_at` 会让一节 3 小时的课在结束仅 21 小时后就被结算。与 §9.2 的迁移条件一致，见 `docs/data-model.md` §7.2。

- 直接来自 §4.4「能自动完成的就不要求老师手动维护」——每天手动点"完成课程"正是最该被自动化的事。
- 老师有 7 天时间用「撤销完成」纠正（§10.5）。
- 之所以默认按"已上课"而非"未上课"结算：这是长期一对一服务关系的商业惯例，且误判时老师可以撤销；反过来若默认不扣课时，老师会频繁发现课时漏扣。
- 老师可把 `auto_settle_hours` 设为 0 关闭自动结算。

**幂等**：自动结算任务必须幂等，重复执行只产生一条 Session（§13）。

## 10.9 老师取消

任意时刻、任意状态（Upcoming）可取消，**永远不扣学员课时**，记 `TEACHER_CANCEL`。时段立即释放。学员收到通知。

# 11. 取消与扣课时规则

**这是 MVP 最容易出现争议的地方，规则集中在此处定义。**

| 取消方 | 时机 | 扣课时 | Session | `policy` |
|---|---|---|---|---|
| 老师 | 任意 | 否 | 不创建 | `TEACHER_CANCEL` |
| 学员 | 距开始 > `free_cancel_hours` | 否 | 不创建 | `FREE_CANCEL` |
| 学员 | 距开始 ≤ `free_cancel_hours`，且未开始 | **扣 1** | **不创建** | `LATE_CANCEL` |
| 学员 | 已开始 | 不可取消（走 §10.8） | — | — |
| 系统 | 自动结算 | 扣 1 | 创建 | — |

## 关键设计：迟到取消不创建 Session

迟到取消扣课时，但**记一条 `PackageTransaction(type = LATE_CANCEL)`，不创建 `Session`**。

这样未来统计时：

- **实际上课** = `Session` 数量
- **临时取消被扣课** = `LATE_CANCEL` 流水数量

两者不会混在一起。老师也不会看到"我明明没给他上课，怎么有一条上课记录"。

## 规则快照

每条 Booking 在创建时快照当时的 `free_cancel_hours`（`policy_snapshot`），后续判定用快照值。老师改规则不影响已有预约。

# 12. 手动调整课时

老师可以：

| 操作 | 场景 | 流水 |
|---|---|---|
| **续课**（默认） | 学员买新一批课时 | 新建 Package + `PACKAGE_CREATED` |
| 增加课时 | 给现有批次补课时 / 纠错加课 | `MANUAL_ADD`（`purchased` 与 `remaining` 同步上涨） |
| 减少课时 | 记多了 | `MANUAL_DEDUCT` |
| 调整到指定值 | `7 → 8` 或 `7 → 6` | **由调用方显式选择** `PURCHASE_ADJUSTMENT`（这批买多/买少了）或 `BALANCE_ADJUSTMENT`（上错课了） |

> ★ **"调整到指定值"必须让老师显式选择纠的是哪一个，不能靠差值正负去猜。**
> `7 → 8` 既可能是"这一批实际买了 8 节"（`PURCHASE_ADJUSTMENT`，两个数一起改），
> 也可能是"少扣了一节、消耗记错了"（`BALANCE_ADJUSTMENT`，`purchased` 一动不动）——
> **同一个差值对应两种完全不同的账本语义**。UI 上要给老师两个明确选项：
> "这批购买量记错了" / "消耗记错了"（iOS 的「调整课时」界面同理，见 `docs/impl-guide.md` §5.6）。
> 由调用方传 `type`，服务端不看正负（`docs/data-model.md` §2.1 / §5.0）。

**任何一次调整都必须产生 `PackageTransaction`，不允许直接改数字。** 备注可选但强烈建议填写（如"上次记录错误"）。

老师端 Student Detail 提供「课时流水」入口，按时间倒序展示：

```
09-18  SESSION_COMPLETED  −1   7 → 6
09-15  续课 +10           +10  0 → 10  （新批次）
09-10  LATE_CANCEL        −1   8 → 7
```

这样遇到"老师，我怎么少了一节？"可以当场完整追溯。

# 13. 并发、幂等与一致性

> **实现平台：自有 REST API（Node.js + TypeScript）+ PostgreSQL 16。**
> 本章描述的并发要求由**数据库约束 + 事务**提供保证：数据库约束负责正确性，应用层负责友好错误。
> 表结构、约束 DDL 见 `docs/data-model.md` §2；事务与锁顺序见 §4、§5。

## 13.1 时间冲突（老师级）

同一老师的任意两条 `Upcoming` Booking 不得重叠（不变式 I3）。这条正确性**由数据库保证**：

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE booking ADD CONSTRAINT booking_no_overlap
  EXCLUDE USING gist (
    teacher_id WITH =,
    tstzrange(start_at, end_at, '[)') WITH &&
  ) WHERE (status = 'Upcoming');
```

应用层的分工变成两件事：

1. **事务内仍然先查一次冲突** —— 不是为了正确性（数据库已经保证了），而是为了给学员一个友好的 `SLOT_TAKEN`：把"这个时间刚被预约，请选择其他时间"这条路走通（§18）。
2. **捕获数据库抛出的排他冲突**：PostgreSQL 的 `exclusion_violation`（SQLSTATE `23P01`）转成 **409 `SLOT_TAKEN`**，绝不能把原始错误抛给客户端。

> **"应用层友好错误"和"底层正确性保证"两层都要有** —— 后者由一条 `EXCLUDE` 约束提供。

## 13.2 课时余额并发

| 场景 | 风险 | 处理（PostgreSQL 实现） |
|---|---|---|
| 两个 Booking 同时完成，余额剩 1 | 余额变 −1 | `CHECK` 约束兜底（I1）；`applyPackageTransaction` 在单事务内对该课包行 `SELECT ... FOR UPDATE` 后扣减 |
| 一个完成、一个逾期取消同时发生 | 重复扣减 | 同上；两条路径都只经该唯一入口 |
| 完成课程与撤销完成并发 | 余额错乱 | `lesson_session` 的部分唯一索引（I2）+ 对 Booking 状态的条件更新，只有第一次能命中 |
| 改期与额度检查并发 | 超额预约 | 改期的新建那一步走创建预约的同一条事务路径，并对 `(student_id, course_id)` 相关行加锁 |
| 两个学生抢同一时段 | 重复占用 | `booking_no_overlap` 排他约束（§13.1） |

**核心手法：所有状态迁移都用条件更新**（PostgreSQL：`UPDATE ... WHERE status = 'Upcoming'` 后检查影响行数 = 1），失败即重试或整体放弃。**不依赖"先读后写"。**

### 关键设计：临界区只包住"创建预约"

**只有"创建预约"需要跨操作互斥** —— 因为它跨越"检查"与"写入"两个时刻。

**取消 / 完成 / 撤销不需要老师级互斥**，因为它们只会让已占用的时段与额度**减少或不变**，并发下读到的值只会偏保守，最坏是多拒绝一次，不会造成超额占用。这让高频操作永远不会因为抢不到锁而失败。

> 在 PostgreSQL 上，完成 / 撤销仍然要在各自的事务里对课包行加锁（否则会丢失更新），但它们**不需要"检查—写入"的临界区**，也不需要一个老师级的锁资源。具体锁顺序见 `docs/data-model.md` §4。

## 13.3 幂等

需要幂等的操作：

| 操作 | 幂等键 |
|---|---|
| 创建 Booking | 客户端生成 `idempotency_key`，服务端 24h 内去重 |
| 完成课程 | 请求级 `idempotency_key` + 状态条件更新双保险 |
| 撤销完成 | 同上 |
| 取消 Booking | 同上 |
| 改期 | 同上（一次改期 = 一个新 Booking + 一个旧 Cancelled，键覆盖整体） |
| 自动结算 | 以 `booking_id` 为天然幂等键 |

实现：`idempotency_record` 表，**唯一性是「主体 + key」**（不是 `(user_id, key)`）。主体用两个可空列
`user_id` / `student_id` 承载，配两条部分唯一索引 —— 因为**免账号学员没有 `user_id`，
而他们的创建 / 取消 / 改期恰恰是最需要幂等的写请求**，所以幂等键挂在 Principal 上，
不是挂在登录账号上（`docs/auth-model.md` §4，DDL 见 `docs/data-model.md` §2.8）。
TTL 24 小时（定期清理过期行）。同一 key 但 `request_hash` 不同 → 返回 409，不执行。

**客户端也要加操作锁**（按钮点击后置 disabled 直到有响应），减少无效请求，但它不是正确性保证。

## 13.4 其他

- 一个 Booking 只能有一条 `Active` Session → 部分唯一索引 `ON lesson_session(booking_id) WHERE status = 'Active'`（不变式 I2）。
- 邀请 token 消费 → 条件更新 `status: 'Pending'` → `Consumed`。
- 学员绑定（不变式 I6）→ 部分唯一索引 `UNIQUE (teacher_id, user_id) WHERE user_id IS NOT NULL`。该索引的语义是：`NULL` 不参与唯一性判断，因此**未绑定学员可以有任意多条**；绑定关系一旦建立，即受 `(teacher_id, user_id)` 唯一性保护。

# 14. 时间处理

- 所有 Booking / Session 的 `start_at` / `end_at` 以 **UTC timestamp** 存储。
- AvailabilityRule / Exception 以**老师本地日期 + 本地时间**存储。
- MVP 固定时区 `Asia/Shanghai`，不做多时区（`TeacherProfile.timezone` 保留字段）。
- 所有面向用户的时间按**老师本地时区**展示。
- 计算"提前 N 小时""距开始 N 小时"时，全部用 UTC 瞬间比较，**不比较本地时间字符串**。
- **后端进程与数据库连接的时区必须显式设为 UTC，禁止依赖运行环境的默认时区**（PostgreSQL 连接参数 `TimeZone=UTC`、Node.js 进程 `TZ=UTC`；容器镜像的默认时区不可信）。见 `docs/data-model.md` §8。

未来进入海外市场再完善多时区。

# 15. 平台能力与合规

## 15.1 使用的能力

| 能力 | 用途 |
|---|---|
| Sign in with Apple | 识别老师与学员 |
| iOS 系统分享面板 | 老师把邀请链接发给学员 |
| 二维码 | 当面邀请 |
| APNs | 预约成功 / 取消 / 改期提醒 |
| EventKit（写入系统日历，可选） | 替代一部分提醒价值 |

> EventKit 是 iOS 上成本很低的一个补偿手段：把已确认的预约写进系统日历，用户自己的日历 App 会按他习惯的方式提醒他。**这不能替代通知，但能补上一部分"提醒"的价值**，而且不依赖任何服务端能力。

## 15.2 通知的真实限制

> **APNs 需要用户授权**：可以拒绝，也可以随时到系统设置里关掉。
> **静默推送不可靠**：低电量、低数据模式、后台被回收时会延迟或直接丢弃。
> **APNs 不保证送达**：它是"尽力而为"的通道，不是消息队列。

因此这里要区分**重要性**与**可靠性**两件事：

- **可靠性判断不变**：APNs 不保证送达，意味着任何依赖推送的机制**都不能承担正确性** —— 推送失败不会、也不能影响任何数据。
- **重要性判断要修正**：**"上课提醒"仍然不能作为产品的核心价值或留存理由**（它会被系统设置关掉、会被低电量延迟），但**"新预约 / 取消 / 改期"这三类面向老师的即时通知是核心闭环的一部分，不是 P1**。
  理由很具体：学员晚上自己约了一节课，老师第二天打开 App 才知道 —— 那么这节课他可能根本不会去上。North Star 是"每位活跃老师每周由学员自主完成的预约数量"（§22.4），而**老师是这条漏斗的对端**：他不知道，闭环就没有闭合。
  因此这三类推送**随真实 pilot 一起上线**（§24 Phase 2）；"完整通知系统"（学员侧提醒、通知偏好设置、上课提醒）仍然留在 Phase 3。
- 通知设计的实际做法：在合适的时机请求一次授权（老师创建第一门课程或第一条预约之后），推送内容**必须可一键跳到那条 Booking**，让老师当场处理。
- **兜底不是"主渠道"，但必须有**：老师打开「今天」时，"新预约 / 待处理"必须是**可见的计数**，而不是埋在列表里。推送丢了（权限被关、APNs 延迟、设备离线）时，这是唯一能补上的地方。
- **学员端 Web 的通知能力更弱**：浏览器通知要用户显式授权，iOS 上还要求"添加到主屏幕"；因此学员侧只做**邮件"尽力而为"**（预约确认 / 取消 / 改期）。邮件同样可能进垃圾箱——这正是 §15.3 要求配好 SPF / DKIM 的原因。

**产品的价值主张中不得出现"自动提醒学员上课"。**

## 15.3 上线前必须确认的前置条件

以下事项影响可行性，**建议在开发 Phase 0 之前确认**，不要做到后期才发现：

1. **Apple Developer Program 账号**：**个人主体即可上架 App Store**，不需要额外的主体资质（见 §21）。若以公司主体上架，需要 D-U-N-S 编码。
2. **Sign in with Apple 的配置**：App ID（含 Sign in with Apple capability）、学员端 Web 所需的 Service ID 与回调域名、服务端验签用的 `.p8` Key。
3. **App Store 审核 5.1.1(v)**：**能创建账号，就必须能在 App 内删除账号。** 实现规则见 §20 的「账号删除与数据保留的冲突处理」，用户故事见 §19 US-9。这是硬要求，不是可选项。
4. **App Store 审核 3.1.1**：App 内消费的数字内容与服务必须走 Apple IAP（§21），且 App 内不得出现引导用户去外部支付的文案或链接。
5. **4.2 最低功能性**：纯 Web 壳或"简单日历"会被拒。本产品的原生价值是「今天」视图、APNs、EventKit 日历写入、系统分享面板；提审材料要把这些讲清楚。
6. **隐私标签与 `PrivacyInfo.xcprivacy`**：申报收集的数据类型（联系方式、用户内容、诊断）与 Required Reason API 的使用理由。
7. **ATT 不适用**：本产品不做跨 App 追踪，不需要 App Tracking Transparency 授权。
8. **自有域名与 TLS**：邀请链接、学员端 Web、API 都需要 HTTPS 域名。**MVP 不需要 `apple-app-site-association`，也不需要 Associated Domains** —— 邀请链接永远在浏览器里打开（§10.2、`docs/impl-guide.md` §8.4）。
9. **中国区上架：后端域名需要 ICP 备案**。自建后端时这是一项硬成本，必须在排期里体现。
10. **邮件发信域名（SPF / DKIM）**：只影响**可选的账号升级路径**（邮箱魔法链接），**不影响关键路径** —— 邀请链接由老师通过系统分享面板发出（§10.2），不经过我们的邮件系统。少一个单点故障。
11. **PostgreSQL 实例、备份与迁移工具**：托管推荐 Supabase（PostgreSQL 16）；本地与生产共用同一套迁移脚本，并在 Phase 0 做一次恢复演练。
12. **密钥管理**：APNs 的 `.p8` 与 Sign in with Apple 的 Key **绝对不能进仓库**。用环境变量 / 密钥管理服务注入，仓库里只放 `.env.example`。
13. **隐私政策与服务条款**：App Store 要求可访问的隐私政策 URL；隐私政策必须写明 §20 的账号删除与匿名化边界（与第 3 条配套）。

# 16. 页面清单

## 16.1 老师端（SwiftUI，底部 4 个一级入口）

**今天 / 日历 / 学员 / 我的** —— 这是 `TabView` 的四个一级 tab；详情与表单用 `NavigationStack` 推入（Booking Detail、Student Detail、Course 编辑等）；**首次设置是独立的 onboarding 流程**（§10.1），完成之后才进入主 `TabView`。

列表统一用 `List` + `.refreshable`，进入页面时用 `.task` 拉数据——**"回到前台要不要刷新"必须显式决定**，不要依赖系统帮你刷新。

| 编号 | 页面 | P0 范围 |
|---|---|---|
| T01 | 今天 / Today | 日期 + 今日课程数；下一节课卡片；**今日课程列表**（时间 / 学员 / 课程 / 剩余课时）；**待处理分组**（§10.8）；快速创建预约；空状态显示下一次课程 |
| T02 | 日历 | **按日列表 + 周切换器**（上一周 / 下一周 / 回到今天）；每日显示 Booking 数与可用时段数；点日期进入当天列表 |
| T03 | Booking Detail（老师） | 学员 / 课程 / 日期 / 时间 / 状态 / 剩余课时；Upcoming：完成课程、标记未上课并扣课时、改期、取消；Completed：查看课时消耗 + 撤销完成；Cancelled：取消时间、取消方、是否扣课时 |
| T04 | Add Booking（老师代约） | 学员 / 课程 / 日期 / 时间；检查冲突（**不检查 Availability**，越权时给出提示，§7.4） |
| T05 | 学员列表 | 搜索；姓名 / 课程 / 剩余课时 / 下一次课程；+ 添加学员；按最近课程时间排序；未绑定标识 |
| T06 | Student Detail | 姓名 / 状态 / 绑定状态（含账号邮箱 / 昵称）；下一次课程；**课包批次列表**（`remaining / purchased` + 状态）；已约 M 节；课时流水；过往课程；操作：续课 / 调整课时 / 创建预约 / 重新发送邀请 / 停用学员 |
| T07 | Add Student | 姓名 → 选课程 → 输入课时数量 → 创建 → 「邀请学员」 |
| T08 | 我的 / Teacher Profile | 老师资料 / 课程 / 开放时间 / 预约规则 / 通知设置 |
| T09 | Course Management | 列表（名称 / 时长 / 状态）；创建 / 编辑 / 停用（**Archive，不 Delete**） |
| T10 | Availability | 每周开放时间（按 weekday，支持多个区间）；临时不可预约（整天 / 区间） |
| T11 | Booking Rules | 最少提前 / 最远可约 / 免费取消期限 / 自动结算 / 改期次数上限 |

> T08 还要多一个入口：**删除账号**（§19 US-9、§20）。

## 16.2 学员端（Web 路由，底部 **2** 个一级入口）

**我的课 / 预约** —— Profile 放右上角。

缩减理由：学员整个生命周期只有"看下一节 + 约一节"两件事（§3.2）。每多一个 tab 都在损耗 R1。

| 路由 | 页面 | 编号 |
|---|---|---|
| `/` | 我的课（首页） | S01 |
| `/book` | 预约（Step1 选日期 → Step2 选时间 → Step3 确认） | S02 |
| `/bookings` | 我的课程（Upcoming / History 两个 Tab） | S03 |
| `/bookings/:id` | Booking Detail（学员） | S04 |
| `/i/:token` | 邀请绑定 | S05 |

| 编号 | 页面 | P0 范围 |
|---|---|---|
| S01 | 我的课（首页） | 老师头像 / 姓名；每个课程卡片：课程名 + 剩余 N 节（§6.6）+ 下一节时间；主 CTA「预约课程」；未绑定状态引导。**匿名会话下固定显示一位老师**；只有账号升级后才显示老师列表（§5.1 决定 6） |
| S02 | 预约 | Step1 选日期（只高亮有可用 slot 的日期，其余置灰）；Step2 选时间（§7.3）；Step3 确认（课程 / 日期 / 时间 / 老师）→ 确认预约 → 成功页 |
| S03 | 我的课程 | 两个 Tab：Upcoming / History |
| S04 | Booking Detail（学员） | 老师 / 课程 / 日期 / 时间 / 状态；Upcoming：改期、取消预约（接近期限时提示"此次取消将计为一次课程"）；已开始：只读 + "请联系老师" |
| S05 | 邀请绑定 | "王老师邀请你加入" + 课程名 + 「接受邀请」→ **直接进入我的课（免账号）**，随后 URL replace 成 `/`（§10.2《回到入口》）；**已消费但会话正是该学员时不算错误，直接进我的课**；已过期 / 已作废 / 无法证明身份的已使用 → 明确提示且**不泄露任何身份信息**；页面内提供一个不显眼的"升级为账号"入口（换设备时用），但**不作为流程节点、不阻塞进入** |

**学员端的约束不变：只有 2 个一级入口 + 零安装 + 无注册墙。**

实现约束：

- 必须在**微信内置浏览器**里可用（学员几乎都是从微信里点开链接的）：不依赖任何 Safari 专有 API，不假设有 `Service Worker`、`Push`、`Add to Home Screen` 能力。
- `/i/:token` 页面必须**自己完整可用**：它是邀请的唯一落地页，任何设备、任何浏览器（含微信内置浏览器）都直接渲染它，不做"请用 App 打开 / 请用 Safari 打开"的拦截。
- 首屏（链接打开 → 看到"X 老师邀请你加入"）要尽可能地快，这是 §22.2 的观测点。

| 老师：Package 已用完 | "已用完" | 「续课」 |
| 老师：Package 处于 `Archived` 状态且有余额 | 提示"归档后剩余 N 节不可用于预约" | 确认后可恢复 |
| 邀请已过期 / 已使用 | 明确文案 + "请联系老师重新发送" | — |
| 时段在确认瞬间被抢 | "这个时间刚被预约，请选择其他时间" + 自动刷新 slot 列表 | 回到 Step2 |

| 网络失败 / 超时 | 保留用户已选内容，可重试 | 幂等键防重复 |
| **App 登录态过期** | 保留当前页面与已填内容，提示"需要重新登录" | 重新 Sign in with Apple 后回到原位置，**不丢已选内容** |
| **邀请链接在任何设备上打开**（装了 App 也一样） | 正常渲染 Web 版邀请页 / 学员视图 | 老师 App 不 claim `/i/*`，不做"请用 App 打开"的拦截（`docs/impl-guide.md` §8.4） |
| **老师账号打开别人的学员邀请链接** | 正常渲染 Web 版学员视图 —— 和学员看到的是同一个页面 | 这是产品明确支持的情形（§5.1 决定 1）；**不做"请用 App 打开"的拦截** |
| **学员在微信内置浏览器里打开邀请链接** | 正常渲染 Web 版，不做"请用 Safari 打开"之类的拦截 | 不依赖任何 App 唤起，不依赖 Safari 专有 API |
| **设备无网络 / 请求超时** | 保留已选（课程、日期、时间） | 重试沿用同一幂等键，不会产生第二条 Booking |
| **通知权限被关闭** | **不阻塞任何功能**；只在「我的 → 通知设置」给出提示 | 提供跳转系统设置的入口 |
| 学员不想注册、也不想登录 | **默认就不需要**：邀请 token 即身份（§5.1 决定 5） | 想换设备时再升级账号；否则老师重发邀请 |

> 上表里「时段在确认瞬间被抢」是最容易被忽略、也最伤体验的一个。**必须有专门的文案和自动回退，不能只弹一个通用错误。**
> 「学员在微信内置浏览器里打开邀请链接」同样必须单独测：这是学员侧最真实的第一跳，走不通就是 R1 直接失守。

# 19. 核心用户故事与验收标准

以下 9 条覆盖 P0 的关键路径，每条都可直接写成自动化测试或人工验收脚本。

### US-1 老师完成首次设置

> 作为老师，我登录后能在 3 分钟内完成课程与开放时间的设置。

**AC**：
- Sign in with Apple 后无需填写手机号即可创建资料
- 创建课程时只需名称 + 时长两个必填项
- 开放时间支持"复制到其他工作日"
- **预约规则可以跳过**，使用默认值（2h / 30d / 24h）
- 全部完成后进入「今天」，且 Today 显示"还没有学员"

### US-2 老师添加学员并邀请

> 作为老师，我能添加学员、给出初始课时，并把邀请发给他。

**AC**：
- 输入姓名 → 选课程 → 输入课时数 → 创建成功，产生一条 `PACKAGE_CREATED` 流水
- 生成 `https://<domain>/i/<token>` 与二维码，可通过 iOS 系统分享面板发出
- **邀请链接在任何设备上都打开 Web 版并完成绑定** —— 包括装了 App 的设备，以及老师自己的账号
- 邀请 7 天后过期，过期后打开提示"邀请已过期"
- 邀请被消费后再次打开，提示"该邀请已被使用"

### US-3 学员绑定（**不需要账号**）

> 作为学员，我在浏览器打开老师分享的链接，不用安装 App、不用注册、不用登录，就能看到我的课时。

**AC**：
- 点「接受邀请」后即建立该学员的会话，`bound_at` 写入，邀请转 `Consumed`
- **全程不出现登录页**，`Student.user_id` 保持为空 —— 这是默认路径，不是失败降级
- 学员首页显示老师姓名、课程名、剩余 N 节、下一节（无则为空）
- 学员看不到任何其他学员的信息
- 重复打开同一邀请不会产生第二条 Student（token 已 `Consumed` → 提示"该邀请已被使用，请联系老师重新发送"）
- **可选升级**：学员主动选择"升级为账号"（邮箱魔法链接 / Apple 登录）后 `user_id` 才被回填；此时"同一账号在同一老师下只能有一条 Student"才开始生效

### US-4 学员自主预约

> 作为学员，我不要问老师就能约到一节课。

**AC**：
- 从打开链接到预约成功 ≤ 3 次点击，**且全程不需要安装 App、不需要注册、不需要登录**
- 日历只高亮有可用 slot 的日期
- slot 列表符合 §7.3（验证：60min 课、14:00–18:00 开放、15:00 已有课时，返回 14:00 / 16:00 / 16:30 / 17:00）
- 确认后 Booking 为 `Upcoming`，`reserved +1`，`remaining` 不变
- 学员端**看不到**已占用时段的原因
- 老师端立刻可见该 Booking

### US-5 学员余额不足时不能超额预约

> 作为学员，我剩 1 节却想约 3 节时，系统要拦住我。

**AC**：
- `remaining = 3`、`reserved = 2` 时，`available = 1`，预约第 3 节成功、第 4 节失败
- 失败时给出明确原因，而非通用错误
- 取消其中一节后，可再次预约（`reserved` 释放）

### US-6 学员取消与扣课时

> 作为学员，我在 24 小时前取消不扣课时，24 小时内取消要提示我会扣。

**AC**：
- `now ≤ start − 24h`：直接取消，无扣减，`policy = FREE_CANCEL`
- `now > start − 24h`：弹出"此次取消将计为一次课程"，确认后扣 1，`policy = LATE_CANCEL`，**不创建 Session**
- 时段在取消后立即回到可预约列表
- **老师中途把 `free_cancel_hours` 从 24 改成 6，已存在的 Booking 仍按 24 判定**（规则快照生效）

### US-7 学员改期（含逾期与额度）

> 作为学员，我能换时间；即使我的课时已被其他预约占满。

**AC**：
- `remaining = 1`、`reserved = 1`，**免费期限内**改期成功（不因 `available = 0` 被拒）
- 新时段与旧时段之间切换是原子的：新 Booking 创建失败时旧 Booking 完好无损
- 免费期限内改期不扣课时
- 逾期改期提示"此次改期将计为一次课程"，确认后扣 1
- **`remaining = 1`、`reserved = 1` 时逾期改期必须失败**（`409 LATE_RESCHEDULE_INSUFFICIENT`），
  且**原 Booking 完好保留为 `Upcoming`、不扣课时**（整体回滚 —— 逾期改期需要额外 1 节可用课时，见 §10.7）
- **`remaining = 2`、`reserved = 1` 时逾期改期成功**：改完后 `remaining = 1`（扣了 penalty）、
  `reserved = 1`（新单）、`available = 0`
- 改期 3 次后不再显示改期入口

### US-8 课程完成与撤销

> 作为老师，我点完成扣 1 节；点错了能撤销。

**AC**：
- 完成课程产生 `Session(Active)` + `SESSION_COMPLETED −1`，`reserved −1`
- **连续点击 5 次只产生 1 条 Session 和 1 条流水**
- 撤销完成后：`Session → Voided`、`REVERSAL +1`、Booking 回 `Upcoming`
- **账本回归**：`10 / 10` → 完成一节课 → 撤销完成 → **必须是 `10 / 10`**。
  `REVERSAL` 绝不能抬高 `purchased`；用 `purchased += GREATEST(amount, 0)` 会得到 `11 / 10`，
  而且 `I1` 仍然成立、任何 CHECK 都不会报错（§5.3、`docs/data-model.md` §1.2）
- 超过 7 天后不再显示撤销入口
- 课程**结束**后 24 小时未处理，系统自动结算为 Completed 且 `source = AutoSettled`

### US-9 老师能删除自己的账号

> 作为老师，我能在 App 里自助删除我的账号，而不用发邮件求人。

**AC**：
- 「我的」页面可见「删除账号」入口
- 发起时需要**二次确认**，并明确写出会发生什么（账号立即失效、教学记录按 §20 匿名化保留）
- 删除后账号与身份标识（`app_user`、`auth_identity`、邮箱、头像、昵称）**立即失效**，无法再登录
- 教学记录（Booking / Session / PackageTransaction / Package）按 §20 的规则**匿名化保留，不物理删除**
- 删除请求有**可审计的记录**（谁、何时、删了什么）
- 删除完成后，学员端不再能看到该老师的可识别身份信息（§20）
- 这是 App Store 审核 5.1.1(v) 的硬要求（§15.3 第 3 条）

### US-10 学员第二次回来（**核心路径**）

> 作为学员，两周后我从微信里翻到老师当初发的那条链接，点进去还应该能直接看到我的课。

**AC**：
- 打开**已消费**的 `/i/<token>`，且当前会话正是该邀请的 Student → **直接进入「我的课」**，不显示"邀请已被使用"
- 接受邀请成功后 URL 立即被 replace 成 `/`，浏览器历史里不长期停留在一次性 token URL 上
- 直接访问 `/`：有学员会话 → 我的课；无会话 → 中性提示，**不展示任何数据**；老师账号 → 引导用 iOS App
- 换一个无会话的浏览器打开同一条已消费链接 → 明确拒绝，且**页面不含老师姓名、学员姓名、课程名**
- 会话不存在时，页面给出"请联系老师重新发送邀请"的明确出路
- 接受邀请后出现一次可关闭的"加入书签 / 添加到主屏幕"提示，且**不阻塞任何操作**

# 20. 数据保留与删除规则

真实业务数据不物理删除（§4.5）。

| 实体 | 规则 |
|---|---|
| Course | 有 Booking → `Archived`；无任何引用才允许删除 |
| Student | 有既往记录 → `Inactive`；无任何引用才允许删除 |
| Package | 有 Transaction → `Archived`；无流水才允许删除 |
| Booking | 只能 `Cancelled` |
| Session | **不删除**，错误时置 `Voided` |
| PackageTransaction | **永不删除、永不修改**（append-only） |
| AvailabilityRule | 软删除（`Deleted`），因为 slot 不落库，删除规则不影响既有记录 |
| AvailabilityException | 可硬删除（不影响任何已存在数据） |
| StudentInvite | 过期的可硬删除 |

**课时修正的唯一途径是追加一条 `PURCHASE_ADJUSTMENT`（这批购买量记错了）或 `BALANCE_ADJUSTMENT`（消耗记错了）流水，不是修改既有流水**（两者不可互换，见 §12 与 §5.3）。

## 20.1 账号删除与数据保留的冲突处理

App Store 要求**能在 App 内删除账号**（§15.3 第 3 条），而本章要求**业务数据不物理删除**。两者并不冲突，因为要删掉的不是同一个东西：

- **删除的是账号与个人身份信息**：`app_user`、`auth_identity`（Apple `sub` / 邮箱）、邮箱、头像、昵称。
- **保留的是业务记录**：Booking / Session / PackageTransaction / Package 涉及**交易另一方的账目**——学员还剩几节课、老师已经上过几节课——**不能因为一方注销而消失**。

因此采用**匿名化 + 停用**，而不是 `DELETE`：

```
账号立即失效（不可登录）
  → 身份标识与联系方式被清除或不可逆处理（如 subject / 邮箱哈希后保留，用于防止重放与风控）
  → 老师资料（姓名 / 头像 / bio）清空为「已注销用户」
  → 教学与课时记录保留，但不再关联任何可识别身份
  → 写一条删除审计记录（时间、账号 id、执行结果）
```

- 这条边界**必须写进隐私政策**（§15.3 第 13 条）。用户以为"删除账号 = 数据消失"是最容易产生投诉的误解。
- 删除请求必须**有可审计的记录**，以应对 App Store 审核与用户投诉。
- 用户故事见 §19 US-9。

> 一句话原则：**删身份，不删账。** 账是双方共有的，身份是自己的。

# 21. 商业模式假设

## 21.1 学员

永久免费。

## 21.2 老师

Freemium SaaS。早期先不收费，验证使用频率。

### Free / Pro 的功能边界

**Free —— 用功能维度限制，不限人数；Pro —— ¥29–39 / 月，或 ¥299–399 / 年。**

| 项 | Free | Pro |
|---|---|---|
| 学员数量 | **不限** | 不限 |
| 课程数量 | 1 门 | 不限 |
| 自主预约 | 支持 | 支持 |
| 课时管理 + 流水 | 支持 | 支持 |
| 免费取消期限 | 固定 24h，不可配置 | 可配置（完整预约规则） |
| 自动结算 | 支持（默认值） | 支持（可配置） |
| **通知** | **新预约 / 取消 / 改期的基础推送** | 上课提醒、可配置提前提醒、通知偏好、多渠道（邮件 / 日历）、导出等**高级能力** |
| 课时流水导出 | 不支持 | 支持 |
| 历史记录 | **可查看最近 90 天历史** | 完整历史 |
| 支持 | 标准 | 优先支持 |

> ⚠️ **推送不能放在 Free 之外。** 老师侧「新预约 / 取消 / 改期」的即时通知是**核心闭环的一部分**（§15.2 / §24 Phase 2）：老师不知道有课，就可能不去上。没有这三种 transactional 推送，Free 产品的核心 loop 本身就是残缺的。
> 因此 Free 与 Pro 的差别在**高级通知能力**（上课提醒、提前量、通知偏好、多渠道），而不在"有没有基础推送"。

> ⚠️ **「可查看最近 90 天历史」限的是「可查看范围」，不是数据保留。** 底层 Booking / Session / PackageTransaction 仍然**永久保留**（§20 的「真实业务记录不物理删除」与账本设计都不变）—— 90 天之后只是界面上不再展示，账目一行未删。

### 收费的前置条件

向老师收订阅费，触碰的是 **App Store 审核指南 3.1.1**：老师 Pro 订阅属于"在 App 内消费的数字内容与服务"，**必须使用 Apple IAP**。代价是：

- **抽成**：首年 30%，次年起 15%；符合条件的小企业计划（Small Business Program）为 15%。
- **价格档位限制**：价格点要落在 Apple 的档位表上，不能任意定价 —— ¥29–39 / 月、¥299–399 / 年这个区间要映射到最近的档位。

理论上也可以只做 Web 端订阅、App 内不提供购买入口。但 **App 内不得出现引导用户去外部支付的文案或链接**（anti-steering 条款），而且这类规则一直在变 —— **提审前必须以当时最新的 App Review Guidelines 为准**，不要照抄本节的条款号与比例。

学员侧是另一回事：

> **学员购买课包属于真实世界的 1 对 1 授课服务，按 3.1.3(e) 可以走 Web 支付，不需要 IAP。**

另外还有一个实际优势：**不用 IAP 就不需要额外的主体资质** —— 个人开发者账号就能上架，也能用 IAP 收款（§15.3 第 1 条）。**因此 Free 阶段不必提前决定主体类型。**

## 21.3 未来

Studio（面向多教练/小型工作室）不属于当前 MVP。

# 22. 指标

## 22.1 Activation

老师是否完成：**创建课程 + 设置 Availability + 邀请至少 1 个学员**。

（预约规则不再是激活条件，因为可以跳过。）

## 22.2 核心漏斗

R1（§2.2）是否被解决，看这条漏斗：

```
老师发送邀请
  → 邀请被打开
  → 首屏跳出        ← 关键观测点：学员端是 Web，多了一跳
  → 绑定成功
  → 首次自主预约
  → 回到入口        ← 第二次打开走的是 / 还是又去点旧链接？（§10.2《回到入口》）
  → 第二次自主预约  ← 真正的判据
```

**「第二次自主预约」必须带观察窗口。** 定义是**首次自主预约之后的 30 天内是否发生第二次自主预约** —— 没有窗口就没法比较 cohort：一个学员是第 3 天回来还是第 200 天回来，对"习惯是否真的改了"是完全不同的结论。

**同时记录 `time_to_second_self_booking`**（首次自主预约 → 第二次自主预约的间隔），并按课程的**实际频率**分组：每周一次的课与每月一次的课，"30 天内第二次"的含义完全不同，混在一起看会得出错误的结论。

**最关键的数字是最右端。** 一次性预约可能是给老师面子；第二次才说明习惯变了。

**「回到入口」这一跳必须单独观测。** 学员第二次回来走的是哪条路，直接决定前面那段回访设计有没有生效：如果大量第二次访问仍然落在 `/i/<旧token>` 上，说明"URL replace 成 `/`"与书签提示没起作用，或者学员的会话已经丢了 —— 此时要修的是回访路径，而不是去优化首屏。

**首屏跳出率是必须重点盯的观测点。** 学员端是"浏览器里的一跳"：链接打开到看到"X 老师邀请你加入"之间的任何延迟、任何要求登录的弹窗、任何"请下载 App"的提示，都会直接吃掉 R1。这个指标变差时，先修首屏，不要加功能。

## 22.3 反向护栏指标

| 指标 | 含义 | 警戒线 |
|---|---|---|
| **老师手动代约占比** | 手动创建的 Booking / 全部 Booking | **> 70% 是一个值得停下来复盘的信号**（观测用警戒线，不是产品定律） |
| 学员自主预约后被取消比例 | 学员自己约了又取消 | 过高说明 slot 质量差 |
| 逾期取消率 | `LATE_CANCEL` / 学员取消总数 | 过高说明规则过严或提醒不足 |
| 自动结算占比 | `AutoSettled` / 全部 Completed | 接近 100% 说明老师根本不打开 App |

最后一条尤其值得盯：如果所有课都是系统自动结算的，说明**老师已经不用这个产品了**，只是账还在跑。这是比"新增用户少"更早期的死亡信号。

## 22.4 North Star

> **每位活跃老师每周由学员自主完成的预约数量**

这个指标最接近核心产品价值：减少人工约课。

## 22.5 Retention

老师是否在第二周仍然：查看课程、接受预约、管理课时。

# 23. MVP 验证标准

如果测试用户出现下面的行为，可以认为方向值得继续：

- 老师开始告诉学员："以后直接在这里约我的时间。"
- **学员在没有老师催促的情况下主动打开链接 / 网页查看可选时间**
- 学员完成**第二次**自主预约
- 老师不再通过 Excel / 备忘录单独记录课时
- 老师一周有多次预约通过系统完成
- 老师开始依赖「今天」确认自己的工作安排
- **学员把邀请链接加入主屏幕书签**（说明它进了学员的日常动线，而不是一次性的）
- **老师开始用 App 的「今天」代替系统日历**（说明它接管了排课这个日常动作）

最关键的信号：

> **产品开始替代微信聊天中的某一类重复沟通。**

反面信号（出现即需重新思考，而不是加功能）：

> 老师仍在微信里问"你周六有空吗"，然后自己手动把课录进系统。

# 24. 开发阶段

按"尽早跑通可测试闭环"重排。**Phase 2 结束时就应该能拿给真实老师试用**，不必等 Phase 4。

## Phase 0 — 使能性前置（对应 §15.3）

- **Apple Developer Program 账号与证书**
- **Sign in with Apple 配置**（App ID / Service ID / `.p8` Key）
- **域名 + TLS**（邀请链接与学员端 Web 的 HTTPS 域名）。**MVP 不需要 `apple-app-site-association`，也不需要 Associated Domains** —— 邀请链接永远在浏览器里打开（§10.2）。将来若要让网页跳进 App，再加 AASA，并**显式排除 `/i/*`**
- **APNs 的 `.p8` 密钥**
- **PostgreSQL 实例 + 迁移工具 + 备份策略**（托管推荐 Supabase，PostgreSQL 16）
- **邮件发信域名（SPF / DKIM）** —— 只服务于可选的账号升级（邮箱魔法链接）；邀请链接走系统分享面板，不依赖我们的邮件系统
- **隐私政策与账号删除流程**（§20）
- **App Store 提审材料**（隐私标签、`PrivacyInfo.xcprivacy`、审核备注）
- **API 服务的鉴权骨架与数据库连接**：所有客户端访问都经 API，**数据库不直接暴露给客户端** —— 这是 §4.3 与 §17 的隐私要求的前提
- **用最小迁移实测三条数据库保证**：`CHECK`、部分唯一索引、`EXCLUDE`（需 `btree_gist`）—— 整套并发判断建立在它们之上
- **时区与时间工具**（UTC 存储 + 本地展示，先从第一天就做对）
  ⚠️ 后端进程与数据库连接的时区必须显式设为 **UTC**，禁止依赖运行环境的默认时区。见 §14 / `docs/data-model.md` §8
- **`applyPackageTransaction` 与单测**（余额的唯一写入口）
- **健康巡检骨架** —— 它是可选监控，不是安全网，可以后置

## Phase 1 — 老师能自己管（单人闭环）

- Course（含 Archive）
- AvailabilityRule + AvailabilityException
- **Slot 生成算法 + 只读查询接口**（先把这块测透，它是整个产品的地基）。**算法在服务端实现，两个客户端都只消费结果** —— 不把时间计算下放到客户端，否则 iOS 与 Web 迟早会算出不同的 slot
- Student + StudentInvite（生成与分享）
- Package（批次模型）+ PackageTransaction
- T01 今天（列表版）、T02 日历（按日列表版）
- T04 手动创建预约 + 冲突检查（§13.1 的 `EXCLUDE` 约束在这一步就要建好）

**里程碑**：老师可以完全用系统管理自己的排课和课时。

## Phase 2 — 学员自主预约（核心闭环）

- 邀请绑定流程（S05）
- S01 我的课、S02 预约、S03 我的课程、S04 Booking Detail
- 创建预约的并发与幂等（§13）
- 取消 + 规则判定 + 规则快照
- **改期（含额度释放方案，§10.7）**
- **老师侧的即时通知**（§15.2）：设备注册、APNs 授权、以及"新预约 / 取消 / 改期"三类推送，**点击直接跳到那条 Booking**
- **通知的投递可靠性与兜底**：投递必须有重试（不能"提交后 `send` 一下就完事"），且「今天」页面必须有**新预约 / 待处理的可见计数**

**里程碑**：`老师开放时间 → 学员自主预约 → 老师当场知道` 跑通。**从这里开始找真实老师试用，iOS 侧用 TestFlight 分发。**

> **为什么通知必须在 Phase 2 而不是 Phase 3**：它不是为了"体验更完整"，而是为了让试点不产生错误的结论。
> 老师不知道有新预约 → 他可能不去上课 → 学员的第二次预约意愿下降 → 我们会误判成"学员不愿意自主预约"（R1 没解决），而真实原因是我们的通知没做。
> **一个会把核心假设测错的缺口，不能留到核心闭环之后。**

## Phase 3 — 结算与收尾

- 完成课程（幂等）
- 撤销完成
- 自动结算任务（§10.8）
- 逾期未处理分组与三个动作
- 课时流水展示页
- 空/异常状态清单（§18）全部覆盖
- 学员侧通知（邮件提醒）与**通知偏好设置**；"上课提醒"这类可被用户关掉的提醒
- T11 预约规则配置

**里程碑**：MVP 完整，可长期运行。

> 排期约束：**API 必须做版本兼容** —— App Store 上的旧版本会长期存在，服务端不能假设客户端已经升级。
